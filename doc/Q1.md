
我正在做一个 Android 人脸识别 Demo，目标是先验证人脸识别核心和低端设备性能。

一、硬件环境

设备：

- SoC：MediaTek MT6762
- CPU：低端多核 ARM，约 2GHz 级别
- RAM：2GB
- 存储：32GB
- 系统：Android 10 AOSP
- 设备没有稳定的 Google Play Services 依赖，最好使用本地打包模型
- 摄像头目前使用前置摄像头
- ImageAnalysis 图像尺寸目前约为 640x480，旋转角度通常是 270 度
- 实际处理后的 Bitmap 尺寸为 480x640

这是一个非常低端的 Android 设备，重点不是追求旗舰机上的实时效果，而是让预览、输入、识别流程尽量可用。

二、项目背景

核心项目是开源项目：

Biometrics-SimFace

它包含：

- simface：人脸检测、人脸对齐、人脸特征提取、1:1 和 1:N 比对
- simq：人脸图像质量评估
- EdgeFace 模型：edgeface_s_gamma_05.tflite
- ML Kit Face Detection：做人脸检测、关键点、轮廓、姿态和分类
- LiteRT/TensorFlow Lite：提取人脸 embedding
- OpenCV：质量分析和图像处理
- EJML：人脸对齐中的矩阵运算

SimFace 的核心流程是：

检测人脸
→ 判断人脸质量
→ 对齐人脸
→ 提取 embedding
→ 保存 embedding
→ 1:1 或 1:N 比对

当前项目不包含真正的活体检测/PAD。

已有能力：

- 人脸检测；
- 人脸框；
- 左右眼、鼻子、嘴角等关键点；
- yaw / roll；
- 质量分；
- 特征向量；
- verificationScore；
- identificationScore。

当前没有：

- 红外活体；
- 深度活体；
- 防照片攻击；
- 防手机屏幕回放；
- 防视频回放；
- 专用 anti-spoofing 模型；
- challenge-response 以外的真正 PAD。

三、原始 Demo 架构

最初的 sample Demo 使用 Jetpack Compose：

- Compose Material3；
- OutlinedTextField；
- Card；
- Column；
- verticalScroll；
- AndroidView 嵌套 PreviewView；
- Compose Canvas 绘制人脸框；
- CameraX ImageAnalysis；
- 每次检测结果更新 Compose 状态。

原始相机分析流程大致是：

ImageProxy
→ 转 Bitmap
→ resize
→ detectFaces
→ 更新 Compose 状态
→ 质量达标后自动抓取
→ 再次 detectFaces
→ alignedFaceImage
→ getEmbedding
→ identificationScore

原始日志表现：

- detectFaces：约 386–531ms；
- 稳定后约 400–500ms；
- imageProxyToBitmap：约 32–36ms；
- alignedFaceImage：约 126–140ms；
- getEmbedding：约 98–102ms；
- identificationScore：约 14–21ms；
- Compose 页面渲染日志：约 0–7ms；
- 但实际输入框曾出现：
  - 工号输入回调间隔约 1.5 秒；
  - 姓名输入回调间隔约 7 秒。

目前无法确定这两个输入延迟到底是：

- 输入法冷启动；
- 主线程调度；
- 内存压力；
- Compose 输入框；
- 用户手动输入间隔；
- 或多个原因共同造成。

四、已经完成的 Demo 改动

为了验证 XML/View 是否更适合低端设备，已经做了一个原生 XML/View 版本的 FaceCamera Demo。

改动包括：

1. 不使用 Compose；
2. 使用 XML + 原生 View；
3. 使用 PreviewView；
4. 使用 CameraX ImageAnalysis；
5. ImageAnalysis 改为：

```java
.setOutputImageFormat(ImageAnalysis.OUTPUT_IMAGE_FORMAT_RGBA_8888)
```

6. 使用现有 rgbaImageProxyToBitmap；
7. 生成 Bitmap 后立即关闭 ImageProxy；
8. ImageAnalysis 使用 STRATEGY_KEEP_ONLY_LATEST；
9. 检测节流约 800ms；
10. 检测任务在后台 Executor 中执行；
11. 主线程只更新 UI；
12. 自动抓取时复用已经得到的 FaceDetection；
13. 自动抓取之后不再重复 detectFaces。

首次 detectFaces：约 1080ms

稳定之后：

推测首次慢可能来自：

- JVM/JIT；
- CPU 升频；
- 内存页加载。

八、当前阈值

当前代码：

```java
public static final float QUALITY_THRESHOLD = 0.4f;
public static final double MATCH_THRESHOLD = 0.6;
```

当前测试中，同一个人的匹配分：

```text
0.967
0.970
0.975
0.977
```

质量分大约：

```text
0.50–0.55
```

需要注意当前比对实现不是原始 cosine，而是：

```text
finalScore = (1 + cosineSimilarity) / 2
```

因此：

```text
MATCH_THRESHOLD = 0.6
等价于 raw cosineSimilarity >= 0.2
```

目前没有真实陌生人数据，因此无法证明 0.6 是否安全。

当前判断：

- QUALITY_THRESHOLD=0.4 适合作为 Demo 初始值；
- 0.4 可能偏宽松，但它主要影响图像质量；
- MATCH_THRESHOLD=0.6 很可能偏低；
- 不能只凭同人分数 0.97 就确定安全；
- 必须采集 genuine 和 impostor 数据后画分数分布；
- 需要计算 FMR 和 FNMR；
- 1:N 还需要考虑 top1 与 top2 的分差；
- 用于登录/门禁时，不能只有 face match。

九、活体检测问题

原项目没有真正的活体检测。

目前的质量分、眼睛睁开概率、yaw、roll 都不是活体检测。

如果直接加入一个活体神经网络，很可能在 MT6762 上造成新的卡顿。

考虑过轻量主动活体：

```text
先做人脸检测和匹配
只有疑似匹配成功后才进行活体
随机要求：
- 眨眼；
- 向左转头；
- 向右转头；
- 回正。
```

优点：

- 不需要每帧运行活体模型；
- 可以复用现有 ML Kit 的 yaw 和眼睛状态；
- 只需要额外检测 2–3 帧；
- 不影响普通预览流畅度。

缺点：

- 只能较弱地防静态照片；
- 可能被预录制视频或智能回放绕过；
- 不属于高安全等级 PAD；
- 会增加约 1–2 秒验证时间。

十、当前真正的问题

当前已经解决：

- Compose UI 过重的问题；
- Bitmap JPEG 往返转换；
- ImageProxy 长时间占用；
- 自动抓取后二次人脸检测；
- 检测任务排队；
- 主线程执行识别的问题。

当前仍存在：

1. MT6762 上单次 detectFaces 仍然约 400ms；
2. 实时检测只能约 1–2 FPS；
3. 首次相机启动约 1.1–1.4 秒；
4. 首次模型/特征提取明显慢；
5. 旋转 Bitmap 仍需要 28–45ms；
6. 尚未有真正活体检测；
7. MATCH_THRESHOLD=0.6 尚未做误识率校准；
8. 尚未证明文本输入卡顿是否完全解决；
9. 尚未测试更多录入人数时的 1:N 性能；
10. 尚未测试不同光照、角度、眼镜、口罩、照片攻击和屏幕回放。

十一、希望获得的新思路

请重点分析：

1. 在不修改 SimFace 核心模型和算法的前提下，如何进一步降低 MT6762 上的 detectFaces 成本；
2. RGBA 方案是否已经足够，还是应该测试 NV21 直转 Bitmap；
3. 是否应该避免实时检测，改成：
   - 预览持续显示；
   - 低频检测；
   - 用户点击拍摄后单次确认；
4. 旋转 Bitmap 是否可以通过 CameraX 配置或坐标变换避免额外 Bitmap 分配；
5. 如何做低成本主动活体，同时不让设备严重卡顿；
6. 如何设计 genuine/impostor 测试集来确定匹配阈值；
7. 如何处理 1:N 人数增加后的性能；
8. 如何区分：
   - UI 卡顿；
   - 输入法卡顿；
   - CameraX 首帧延迟；
   - 人脸检测慢；
   - LiteRT 冷启动；
9. 这台 2GB AOSP 设备是否适合持续实时人脸认证；
10. 哪些功能应该改成单次拍摄、低频检测或异步确认。

十二、重要限制

- 不要建议直接修改 SimFace 核心检测算法，除非明确说明风险；
- 不要假设 0.8、0.85、0.9 任何一个阈值天然安全；
- 不要把质量分当成活体分；
- 不要把“同人得分高”当成“陌生人一定得分低”；
- 不要为了实时预览在后台并行跑多个 400ms 检测；
- 不要在主线程做 Bitmap、ML Kit、LiteRT 或 OpenCV 工作；
- 当前目标是低端设备上稳定、可验证、可测量的人脸 Demo。
